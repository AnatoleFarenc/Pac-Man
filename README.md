# Description

The goal of this project is to create our own version of the classic video-game PAC-MAN.
The project was coded in Python using **pygame-ce** and uses a external **mazegenerator** package for the level generation.

The game includes all the basic mechanics of the original: a movable player, ghosts that chase you, pacgums and superpacgums to pick up, and a full 10-level replayable game, with high-score registering and modifiable config.

We quickly decided to add just a slight change in our version: a third dimension !
Yes you read that correctly: we decided to write our PAC-MAN in 3d (using ray-casting like in the classic DOOM video game). This is our tribute to the classic Cub3D raycasting project.

# Config

There is a user-modifiable config file, located at `.data/config.json`, where some game values can be modified (ex: lives, points per pacgum, level size... etc).

```json
{
	"width": 15,
	"height": 15,
	"lives": 3,
	"points_per_pacgum": 10,
	"points_per_super_pacgum": 50,
	"points_per_ghost": 200,
	"seed": 42,
	"level_max_time": 500,
	"max_levels": 10,
	"highscores_filename": "./data/high_scores.json"
}
```

This config file can be passed as an argument to the program. This config can further be modified in the game itself, but the changes made in the game won't be written to the file. To make permanent changes, please modify the config file directly.

In any error case with the config file (invalid path, incorrect format, invalid values), the game will still launch with defaults config values replacing the problematic ones.

# High-scores

The high-scores system works almost like the config. The high-scores are contained in a json file (no score files is present on the first launch, it will be created as soon as a score is set).

The files contains the name and score of the 10 best players at maximum. When a new high score is made, the list is updated accordingly, and written to the json file, to ensure persistent high-scores through multiple runs.

The high-scores can be accessed through the main menu.

# Maze Generation

To generate the levels, we use the external mazegenerator package that comes from a maze generation project called A-maze-ing.
We use this package inside our `Map` class, to generate levels with the size given by the config.
We generate imperfect mazes by default, to make the game playable and fun (a perfect maze would always result in player death anyway).

# Implementation

## State Machine

The whole game logic works with a State Machine, consisting of several `GameState` enum members:

```python
class GameState(Enum):
    """All possible states of the game's top-level finite state machine."""

    MAIN_MENU = auto()
    PLAY = auto()
    HOW_TO = auto()
    HIGH_SCORES = auto()
    SETTINGS_MENU = auto()
    QUIT = auto()
    PAUSE_MENU = auto()
    CHEAT_MENU = auto()
    VICTORY = auto()
    FINAL_VICTORY = auto()
    GAME_OVER = auto()
    ENTER_NAME = auto()
```

This allow us to control the game flow using these states, and a lot of state dependent tasks (ie. menu rendering) becomes way easier this way.

## Maze display
Being that we wanted to develop our project in 3D, we had to adapt the map generated by the **MazeGenerator** so that it would be compatible with the **raycasting** system.

### Raycasting

To create a 3D effect, we chose to use **raycasting**. This technique makes it possible to render a 2D map as a pseudo-3D environment. The game **Doom** is a well-known example of a game that uses this technique.

The principle consists of defining a cone that represents the camera's viewing angle, known as the **FOV** (*Field of View*). Within this cone, rays are cast in straight lines from one side of the field of view to the other. When a ray hits an obstacle, its length is used to calculate the distance to that obstacle. The obstacle is then drawn with a size proportional to this distance, creating the illusion of depth.

### Mini-Map

Since the game is now displayed in 3D, navigating through the maze became more difficult. To address this issue, we decided to add a mini-map centered on the player.

The mini-map does not display the entire maze, but only the area surrounding the player. It also shows pac-gums, super pac-gums, and ghosts. When ghosts are too far away to appear within the displayed area, they are shown along the edge of the mini-map to indicate the direction in which they are located.

### Sprites

As explained earlier, **raycasting** does not produce true 3D graphics but rather a visual illusion. Because of this limitation, it is not possible to render these objects as fully 3D models.

For this reason, ghosts, pac-gums, and super pac-gums are displayed as 2D sprites. These sprites always face the player regardless of the viewing angle, ensuring that they remain visible and maintain the illusion of existing within the 3D environment.

## Menus

For the game menus, I decided to go fully object-oriented, and I also used abstractions.
Each menu class is a child from the `Menu` abstract class, because they share a lot of underlying logic and using this abstract class allow us to avoid a lot of code duplication.

Each menu has its own `render()` method (or uses the default implementation), and they all implement a concrete `handle_key()` method that allow the user to interact with the menu.

This object-oriented approach saved us a lot of time because adding a new menu was then a really simple task. Each menu contains a title, a list of items, and other special data depending on the menu (high-scores, settings.. etc).

Here is a quick overview of each of the modules and their uses:
- `config`: handle the config and high-score import/export, and stores project constants.
- `entity`: handle all the in-game interactive entities (ghosts, pacgums... etc).
- `game`: contains the `Game` master object, main pygame loop and gamestates.
- `game_engine`: contains the meat of the player and interface (player, hud, map, mini_map, cheats...).
- `interfaces`: contains interfaces `HasTransform` and `Setting`.
- `menus`: contains all the abstract and concrete classes used for menu logic and rendering.
- `utils`: contains different utils, (for display, visual fxs... etc).

# Project Management

From the start of the project, we quickly planned what would be done by who and when.
Anatole worked on the graphical/raycasting side of the project, while Benjamin worked on the menus, the game loop and backend-like stuff, like ghost pathfinding, player/ghost state handling.

At the beginning, we wanted to do the game in real 3d using OpenGL. After getting acustomed briefly with it, Anatole realized the workload would quickly becomes really long and complex, and for the sake of efficiency, we decided to finally settle on Doom-like raycasting inside pygame.

After that things went smoothly. Ben worked on the different menus, while Anatole was getting the first displayable results. We then joined our parts so that the first display version (ie. walking in the maze with a basic camera) could be launched from the main menu.

As Ben choosed to go with a object-oriented menu suite, the whole menu implementation took a lot of time, but the result would be a easily reusable and modulable menu system.
During the next days, Anatole fleshed out the ghosts appearance and how they would be displayed in the maze, while Benjamin implemented the ghost pathfinding. Anatole added a fully fonctional adaptative minimap, to simplify the user experience and make the HUD cleaner.

The last week of the project was spent fine-tuning the different parts of the game, cleaning up unused code.

You can find traces of our teamwork inside the [project_management](project_management/) folder.

# Instructions

The project uses [uv](https://docs.astral.sh/uv/) as its Python package manager. Run `make` with no arguments to see all available commands.

| Command | Description |
|---|---|
| `make install` | Install all dependencies via `uv sync`, including the bundled `mazegenerator` wheel |
| `make run` | Launch the game with the default config (`data/config.json`); pass `CONFIG_PATH=...` to use a custom one |
| `make debug` | Run the game with `pdb` attached |
| `make lint` | Run `flake8` and `mypy` with moderate strictness |
| `make lint-strict` | Same as `make lint` but with `mypy --strict` |
| `make build` | Create a `pac-man.tar.gz` archive of the project |
| `make clean` | Remove `.venv`, `.mypy_cache`, and all `__pycache__` directories |
